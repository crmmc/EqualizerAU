## 背景

EqualizerAPO 以文本配置和默认 Instant mode 为中心。EqualizerAU 还需要稳定节点身份、
节点启用状态、声道选择、草稿历史、恢复状态和音效总开关，因此直接把编辑器文本或每次
控件变化当作运行时事实来源，会把格式兼容、用户编辑和实时发布绑在一起。

同时，M1 允许多个 Preamp，但实时层只接收控制层编译后的固定每声道目标。配置可以在
暂时没有输出布局时保持结构合法，却不能因此猜测声道或构造占位运行时对象。

## 决策

1. `config.json` 是唯一可写的持久配置事实来源，使用带 `schemaVersion` 的原生 typed JSON。
2. EqualizerAPO 文本不作为并列可写配置源；后续只通过显式导入或导出进行转换。
3. 配置草稿只存在于当前应用会话，不改变声音、不参与重启恢复，也不写临时恢复文件。
4. 用户通过显式 Save 提交整份不可变节点草稿快照；不提供节点编辑 Instant mode。
   音效总开关不属于节点草稿，按 <PII type="CASE_ID" id="675"/> 的独立实时与持久化语义处理。
5. Save 的设备无关校验通过后，即使当前没有有效输出布局也允许持久化；取得真实布局后
   才编译和发布，不猜测声道、不构造占位 `PreparedDSPChain`。
6. 不设置固定节点数量上限。配置和 typed 剪贴板分别以规范 UTF-8 编码后的 `4 MiB`
   为硬上限，超限操作整体拒绝；限制依据序列化资源，而不是任意节点数量。
7. Undo 与 Redo 两栈合计最多 `30` 条、规范历史载荷合计不超过 `64 MiB`；当前草稿和
   独立已保存比较基线不计入历史载荷，但各自仍受配置大小限制。

## 理由

| 关注点 | 采用方案的收益 |
|---|---|
| 数据模型 | UUID、类型和状态有明确 schema，不依赖文本注释或编辑器内部表示 |
| 用户控制 | 节点草稿可撤销，只有明确 Save 才改变节点持久状态和声音；音效总开关保持独立即时语义 |
| 实时安全 | 文件不是控制层与实时层的通信通道，发布前必须完成校验和编译 |
| 无设备编辑 | 用户配置保持设备无关，不用错误布局污染持久选择 |
| 互操作 | EqualizerAPO 转换有明确边界，不会形成两个可写事实来源 |
| 资源安全 | 字节预算能约束 JSON、剪贴板和历史内存，同时不制造无依据节点上限 |

## 备选方案

| 方案 | 不采用原因 |
|---|---|
| EqualizerAPO 文本作为主格式 | 难以稳定承载 UUID、typed 状态、恢复和版本迁移 |
| 每次控件变化立即写盘和应用 | 与草稿、Undo、失败保留和可恢复提交冲突 |
| 数据库或二进制配置 | 首版不需要其复杂度，也不利于可读和版本管理 |
| 固定节点数量上限 | 没有产品依据；M1 实时工作量与节点数无关 |
| 无布局时拒绝 Save | 不必要地阻止设备无关配置编辑和恢复 |

## 后果

- 配置编辑器必须明确区分草稿、已保存配置和活动处理代次；
- Save 需要捕获不可变候选，后续编辑不能改写在途提交；
- 后续 schema 语义变化必须提升版本并定义迁移或拒绝规则；
- EqualizerAPO 导入或导出属于独立功能，不能直接绕过原生校验；
- 资源预算会产生用户可见的整体拒绝或历史淘汰，必须提供明确错误或状态。

## 重新评估条件

- 原生 JSON 无法表达已承诺的处理节点或迁移需求；
- 产品决定把 EqualizerAPO 文本升级为可双向编辑的主要工作流；
- 实测表明当前字节预算不能覆盖正常配置，或造成不可接受的内存压力；
- 产品要求未保存草稿跨崩溃恢复。
